# Cooperative tabu search for the MDMKP: solutions, data and verification

This repository holds the solutions, the run records and the verification scripts of the computational study of COTS,
a cooperative tabu search for the multi-demand multidimensional knapsack problem (MDMKP), implemented on a GPU
(COTS-GPU) and on a CPU (COTS-CPU). It covers 120 benchmark instances with 100, 500 and 1000 items, the
comparison with equal computational resources on the CPU and the 180 instances of Scherer (2024). Every solution
can be checked with the scripts included here, which use only the Python standard library.

## Results

COTS-GPU performed independent runs with seeds 1, 2, ... on every benchmark instance (1200 runs):

| Items | Instances | Runs per instance | Time limit | Best value above the published best |
|---:|---:|---:|---:|---:|
| 100 | 30 | 10 | 60 s | 3 |
| 500 | 30 | 10 | 600 s | 25 |
| 1000 | 60 | 10 | 600 s | 45 |

The published best of an instance is the largest best value published for it by TSTS, CORE-LP-LS-TSTS, CP-LB-MS and
AF, together with the best-known values (BKV) published for the instances with 500 items
(`data/reference_values.csv`). The best value of COTS-GPU exceeds the published best on 73 instances, 62
of them among the 104 instances held out from the design pilots and the selection of the configuration
(`data/campaign/summary.csv`, columns `new_best` and `development`).

On the 180 instances of Scherer (2024), one run of COTS-GPU per instance is better than the best value
distributed with the instance on 1, equal on 167 and below it on 12
(`data/scherer/results.csv`).

## Verify the solutions

Python 3.8 or later is required.

```sh
python scripts/download_instances.py
python scripts/verify_solutions.py
python scripts/verify_scherer.py
```

`download_instances.py` obtains the instances with 100 and 500 items from the archive `benchmark.zip` distributed by
Lai, Hao and Yue (2019), which contains the OR-Library instances of Cappanera and Trubian (2005), the instances with
1000 items, generated by Al-Shihabi (2025), from the repository
[samehShihabi/MKMP-instances-1000](https://github.com/samehShihabi/MKMP-instances-1000) at commit `a962b7b`, and
the file `MDMKP_Instances.txt` of Scherer (2024) from Mendeley Data. It checks the SHA-256 of every file against
`data/instances_source.json` and `data/instances.csv` and writes the instances to `instances/`, keeping the files
already there with the right digest. Local copies can be given with `--archive`, `--dir1000` and `--scherer`. The
instances are distributed by their authors.

`verify_solutions.py` re-reads every benchmark instance, checks every capacity row and every demand row of every
solution, and recomputes its profit and its number of items. It then checks that the run tables, the traces, the
per-instance summary, the best-solution files, the reference values, the isolation table and the records of the
passages agree with the verified solutions. With `--isolation` it also recounts the feasible neighbours of the best
solution of every instance, which takes a few minutes.

`verify_scherer.py` re-reads the instances of Scherer (2024), checks every solution in exact rational arithmetic on
the original data, recomputes its profit and compares it with the best value distributed with the instance (profits
within 1e-6 of it count as equal). It also rebuilds the integer instance that COTS-GPU solved, with the coefficients
multiplied by 1000 and rounded conservatively, and checks its SHA-256. With `--isolation` it recounts the feasible
neighbours of every solution in exact arithmetic.

The evaluators have unit tests:

```sh
python -m unittest discover -s scripts
```

## Contents

- `data/instances.csv`: group, instance label used in the manuscript, file, source, size, SHA-256 and dimensions of
  every benchmark instance; `data/instances_source.json`: the three sources.
- `data/development_instances.csv`: the 16 instances used in the design pilots or in the selection of the
  configuration, with the stages that used them. They are marked with a dagger in the tables of the manuscript, and the
  comparison on the hold-out instances uses the remaining ones.
- `data/reference_values.csv`: the best value and the average published for each method, exactly as printed in the
  source tables, the published best and the methods that attain it; `data/reference_sources.csv` gives the source
  table of each column. 6 published values contradict the other values published for their instance; the column
  `inconsistent` lists them, and they are left out of the published best and of the comparisons of the manuscript.
- `data/campaign/`: `runs.csv` (one row per run: profit, number of items, time at which the run reaches its best
  value, wall time, iterations summed over the trajectories, number of trajectories and of intensifiers, time limit,
  and the SHA-256 of the kernel and host files), `traces.csv` (every improvement of the best value of each run, with
  the trajectory that found it and its role) and `summary.csv` (one row per instance).
- The mechanism experiments of the manuscript on the GPU, on six instances with 1000 items, with `data/variants.csv`
  describing every variant and the runs it is paired with:
  - `data/ablation/`: 6 variants that each remove or restrict one component, on 6 instances with seeds 1 to 3 and runs of 600 s (108 runs).
  - `data/interaction/`: 2 variants that remove two components, on 6 instances with seeds 1 to 3 and runs of 600 s (36 runs).
  - `data/cooperation/`: 3 variants without the sharing of the best selection or with 16 trajectories, on 6 instances with seeds 1 to 3 and runs of 600 s (54 runs).
  - `data/sensitivity/`: 8 variants that each change one parameter, on 6 instances with seeds 1 to 2 and runs of 600 s (96 runs).
  - `data/behaviour/`: the reference configuration on the same 6 instances with seed 1 and runs of 600 s, sampled every 5 s without altering the search (`samples.csv`; 6 runs).
  - `data/tuning/`: the two rounds of the selection of the configuration, each with a screening and a confirmation, on 13 instances with seeds 1 to 3 and runs of 120 s or 600 s (234 runs).
- `data/equal_resources/`: the comparison with equal computational resources on the eight performance cores of the
  CPU (1320 runs, 534 of them of TSTS). `runs.csv` has one row per run: experiment, variant, program, time
  limit, hardware threads, trajectories and intensifiers of COTS-CPU, profit, number of items, time at which the run
  reaches its best value, wall time, steps and restarts of COTS-CPU, and the SHA-256 of the source and executable of
  the program; `traces.csv` holds every improvement of the best value of each COTS-CPU run and `programs.csv` the
  programs with their digests. The experiments are `pilot` (1, 4 or 8 trajectories on one core), `one_core` (TSTS and
  COTS-CPU with one trajectory, seeds 1 to 5; COTS-CPU receives the time that TSTS used with the same instance and
  seed), `sixteen_threads` (16 independent TSTS runs, COTS-CPU with 16 cooperating trajectories and 16 independent
  COTS-CPU runs, on the sixteen hardware threads) and `design`, `design2` and `design3` (COTS-CPU with one trajectory
  on one core and its variants), all described in `data/variants.csv`.
- `data/passages/`: the passages to the improvements of the best value in the runs `design2/paths`.
  `events.csv` (4898 rows) has one row per improvement: trajectory, time, profit, `kind` (0 construction, 1 tabu
  walk), `above` (1 when the improving move was taken in the above-record mode), `move` (0 addition, 1 drop, 2 swap,
  -1 construction), `len` (consecutive infeasible selections visited since the walk last held a feasible one),
  `maxrows` and `maxviol` (largest number of violated rows and largest total violation along the passage), `maxrank`
  and `lastrank` (largest rank of an outgoing item along the passage, including its last move, and the rank of the
  last move, in the order of the list of 8 outgoing items), `ham_prev` and `ham_start` (Hamming distance of the new
  best to the previous best and to the selection from which the walk restarted), `since_restart` (steps since the last
  restart) and `restarts`. `counters.csv` gives, per run, the steps of the tabu walk, those on infeasible selections,
  the steps of the passages that end in a new best together with their improving step (`productive_steps`), and the
  excursions out of the feasible set that end in a new best, that return to a feasible selection without one, or that
  end at a restart.
- `data/scherer/results.csv`: for each of the 180 instances of Scherer (2024), one run of COTS-GPU with seed 1
  and 60 s (64 trajectories, 75 % intensifiers, deletion range 1-5 %, L = 30000, construction temperature 1, penalty factor 1.1) on the coefficients multiplied by 1000 and rounded conservatively: the
  exact profit on the original data, the best value distributed with the instance and their comparison, the size of
  the add/drop/swap neighbourhood of the solution and its feasible and improving neighbours (0
  isolated solutions), and the SHA-256 of the integer instance, kernel and host files. `prescribed_correlation` is 1
  for the instances generated with prescribed correlation structures.
- `data/isolation.csv`: for the best solution of every benchmark instance, the size of its add/drop/swap
  neighbourhood, the number of feasible neighbours and the number of feasible neighbours with a higher profit.
- `data/code_digests.csv`: the SHA-256 digests of the kernel and host files of each GPU experiment;
  `data/equal_resources/programs.csv` those of the CPU programs.
- `solutions/`: the solution of every run, as selected items numbered from 0, in one file per experiment;
  `best/n<items>_<instance>.json` holds the best solution of each benchmark instance (the smallest seed attaining the
  best value of the campaign).
- `PUBLIC_EXPORT_MANIFEST.json`: export date, number of runs of each experiment and SHA-256 of every file.

The implementations of COTS are maintained separately; `data/code_digests.csv` and
`data/equal_resources/programs.csv` identify the files of every run.
